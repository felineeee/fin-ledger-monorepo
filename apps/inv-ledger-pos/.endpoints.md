### Authentication (Microservice)

### Locations

- `[x] GET /api/locations` — List all stores, warehouses, and virtual zones
- `[x] GET /api/locations/:id` — Get single location details
- `[x] POST /api/locations` — Create a new location (`STORE`, `WAREHOUSE`, or `VIRTUAL`)
- `[x] PATCH /api/locations/:id` — Update location details or deactivate (`is_active: false`)

### Inventory Levels

- `[x] GET /api/locations/:id/inventory` — Fetch current `inventory_levels` for a specific store (paginated — limit/offset required, this can grow large)
- `[x] GET /api/locations/:id/inventory/:productId` — Get real-time stock level for a single product at a specific location (response includes reorder_threshold inline — no separate GET needed for it)
- `[x] GET /api/products/:id/inventory` — View stock level breakdown across all locations for a specific product
- `[x] PATCH /api/locations/:id/inventory/:productId/reorder-threshold` — Set minimum reorder point threshold for a product at a specific location
- `[x] GET /api/inventory/low-stock` — Cross-location view of products falling below reorder point
- `[x] POST /api/inventory/adjust` — Perform manual stock adjustments; updates inventory_levels and writes a SHRINKAGE (negative delta) or CORRECTION (positive delta) record to inventory_ledger, determined by the sign of quantityDelta. Returns 404 if no inventory_levels row exists yet for this (locationId, productId) pair — this endpoint corrects existing stock, it does not initialize new stock (that only happens via PO receiving, transfers, or returns in later phases).

### Audit Ledger

- `[x] GET /api/inventory/ledger` — Query audit trail filterable by product, location, or date
- `[x] GET /api/inventory/ledger/:id` — Retrieve single ledger entry details for deep audit drill-downs

## 2. Phase 2: Purchase Orders (Supplier Procurement)

### Suppliers

- `[x] GET /api/suppliers` — List all suppliers and contact details
- `[x] GET /api/suppliers/:id` — Get single supplier details
- `[x] POST /api/suppliers` — Register a new supplier
- `[x] PATCH /api/suppliers/:id` — Update supplier details or deactivate (`is_active: false`)

### Purchase Orders

- `[x] GET /api/purchase-orders` — List POs with optional filtering by status
- `[x] GET /api/purchase-orders/:id` — View full PO details and nested line items
- `[x] PATCH /api/purchase-orders/:id` — Edit line items and quantities while PO is still DRAFT
- `[x] POST /api/purchase-orders` — Create a `DRAFT` PO with requested items and quantities
- `[x] PATCH /api/purchase-orders/:id/status` — Transition PO state (`DRAFT` -> `SENT` / `CANCELLED`)
- `[x] DELETE /api/purchase-orders/:id` — Hard-delete an un-sent `DRAFT` PO

### The Receiving Engine

- `[x] POST /api/purchase-orders/:id/receive` — Process inbound scanned items, update `quantity_received`, increment `inventory_levels`, and write `RECEIPT` to `inventory_ledger`
- `[x] GET /api/purchase-orders/:id/receipts` — Historical breakdown of partial receiving events against a PO

## 3. Phase 3: Inter-Branch Transfers

### Transfer Management

- `[x] GET /api/transfers` — List stock movement requests
- `[x] GET /api/transfers/:id` — View specific transfer manifest and item breakdown
- `[x] GET /api/locations/:id/transfers/incoming` — Filtered view: transfers destined for this location
- `[x] GET /api/locations/:id/transfers/outgoing` — Filtered view: transfers originating from this location
- `[x] POST /api/transfers` — Submit a transfer request between locations
- `[x] PATCH /api/transfers/:id/cancel` — Cancel a transfer while status is `PENDING` (before dispatch)

### Dispatch & Receive Flow

- `[x] POST /api/transfers/:id/dispatch` — Deduct stock from origin `inventory_levels`, write `TRANSFER_OUT` to ledger, and update status to `IN_TRANSIT`
- `[x] POST /api/transfers/:id/receive` — Increment stock at destination `inventory_levels`, write `TRANSFER_IN` to ledger, and complete transfer
- `[x] POST /api/transfers/:id/reject` — Destination location refuses damaged or wrong shipment (routes stock to quarantine or resolution path)

## 4. Phase 4: Stocktakes & Cycle Counting

### Stocktake Management

- `[x] GET /api/stocktakes` — List active and historical counts
- `[x] GET /api/stocktakes/:id` — Fetch stocktake status and list of snapshot items to count
- `[x] POST /api/stocktakes` — Start a new count session, taking a snapshot of `inventory_levels` to populate `expected_quantity`
- `[x] DELETE /api/stocktakes/:id` — Cancel/abort an `IN_PROGRESS` stocktake session (e.g. operator error)

### Counting & Reconciliation

- `[x] POST /api/stocktakes/:id/count` — Submit batch barcode scans to update `counted_quantity`
- `[x] PATCH /api/stocktakes/:id/count/:itemId` — Correct a single miscounted item quantity before finalizing
- `[x] GET /api/stocktakes/:id/variance-report` — Review expected vs. counted discrepancies before committing adjustments
- `[x] POST /api/stocktakes/:id/complete` — Lock stocktake, calculate variances, update `inventory_levels` to match reality, and write `ADJUSTMENT` / `SHRINKAGE` to `inventory_ledger`

## 5. Phase 5: Reverse Logistics & Quarantine

### Returns & Disposition

- `[x] POST /api/returns` — Process customer return into virtual quarantine location (writes RETURN to ledger)
- `[x] POST /api/returns/:id/restock` — Move pristine item from quarantine back to sales floor
- `[x] POST /api/returns/:id/discard` — Write off damaged item from quarantine (writes DAMAGE to ledger)
